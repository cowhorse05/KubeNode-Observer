# 2026-10-27 Kata Host 接入与可见性边界

## 目标和实际交付

基于已合入 PR #4 的 main `1b768a5`，分支 `codex/kata-host-integration`。`0c26512` 实现运行时感知拓扑及官方 Monitor 转发，`76063cf` 加入离线安装、测试与指南。本阶段是 M7，不提前把 M8/vCPU eBPF 或 M9/Guest Probe 记为完成。

交付链路：CRI Ready Sandbox → 完整 ID 匹配的 Host Kata shim → 唯一 VMM 子孙进程 → Host PID/starttime/cgroup → Pod 身份。应用容器列表与 VM 列表分开；应用重启期间 VM 仍可存在。Snapshot 的 `sandboxes` 每 VM 一条，不以容器数复制 VMM。

复用官方 Kata Monitor 提供的 Host/Guest 聚合指标，项目没有重写 hypervisor、shim、Guest Agent、Prometheus parser 或 Guest 探针。原 `/metrics` 仍是本项目自监控。使用方法、所有字段含义及回滚步骤见 [Kata 指南](../docs/kata.md)。

- containerd 默认仍为 runc，只有 RuntimeClass `kno-kata-qemu` 选择新增的 `kata-qemu` handler。Observer 200m/128 MiB 不变。

## 尝试一：KVM 检查通过，但真实 Guest 启动失败

节点内存在 KVM/vhost 设备；实际 `KVM_GET_API_VERSION=12`，`KVM_CREATE_VM` 成功；官方 `kata-runtime check` 也认为可运行。它们只说明基础条件，不证明完整 Guest 能启动。

[首次边界测试](kata-test-20261027/exit.json) 失败，保存 [启动日志](kata-20261027/first-boot-journal.txt) 和测试目录的 failure 记录。runc 对照可运行，Kata 持续 ContainerCreating：QEMU 已选择 `accel=kvm`，随即报 `error: kvm run failed Bad address`，之后 Guest vsock 连接超时。

排查发现 Minikube Docker 容器的 `HostConfig.ShmSize=67108864`，现场 `df` 显示 `/dev/shm` **64 MiB 全满**；其后保存的 [清理后样本](kata-20261027/shm-after-failure.txt) 已释放，不将该文件冒称故障时满载采样。QEMU 的 512 MiB Guest RAM 使用 `/dev/shm` 的共享 backing，解释了“空 VM 可创建、真正触页失败”。这是节点容器 tmpfs 容量问题，不能仅凭 vCPU 转储认定是 Hyper-V/WSL 不支持嵌套虚拟化。上游有 [相同故障机制报告](https://github.com/kata-containers/kata-containers/issues/12919)。

## 尝试二：只调整节点私有 tmpfs，独立重跑通过

没有更换 CPU feature、Guest kernel、QEMU、节点内核或 Windows 设置，只将节点 mount namespace 的 `/dev/shm` 上限 remount 为 **1 GiB**。[调整后样本](kata-20261027/shm-resized.txt) 保留。

同一第一版 Agent 镜像的 [第二次边界测试](kata-test-v2-20261027/exit.json) 独立通过，失败时长未计入成功。安装器随后固化此设置；受管 `kno-kata-shm.service` 在 containerd 前执行，已实际 start 并核对 enabled/active。未重启整台 Windows/WSL/Minikube 来验证断电恢复，不能把 systemd 配置检查说成已验证了所有重启情形。

1 GiB 是容量上限而非预分配；节点总 memory limit 和 Agent budget 未提高。它仅是本阶段单 VM 开发设置，多 VM/更大 Guest 仍需独立规划 tmpfs、调度 overhead 与节点内存。

## 最终实现回归：一次共享 VM，而非两份容器记账

改进为从 CRI Ready Sandbox 独立保留 VM 后，最终镜像 `sha256:f806e0c4cb6661589263e81321f3b063fa5f11f4503f72c62caaeae6dfcd6972` 的 [第三次完整边界测试](kata-test-v3-20261027/exit.json) 通过，保存源码 HEAD/文件 SHA256、Pod 状态、CRI、Host fd 和原始 metrics。

| 检查 | 实际结果 |
| --- | --- |
| 内核边界 | runc `6.6.114.1-microsoft-standard-WSL2`，Kata `6.18.56` |
| 双容器 | exec/cpu 两容器都 Running，拓扑仅一条 Sandbox |
| CRI PID 陷阱 | 两个容器的 CRI PID **均为 613124**，正是 VMM PID，不是 Guest 各自的宿主 init PID |
| Host 身份 | shim 613099，QEMU 613124；完整 Sandbox ID、Pod UID 匹配，无 discovery issues；QEMU fd 中存在 `/dev/kvm` 与 `kvm-vm` |
| Guest 安全边界 | 两容器 `processVisibility=guest-unavailable`、pid=0、无普通 Host container cgroup/进程列表；VMM 不进普通容器 Resolve 索引 |
| exec 正负对照 | 分别在 runc/Guest 执行 5 次 `/kno-boundary --child`；Host 记录 runc 的 5 exec/5 exit，未记录 Guest 同名 exec |
| Monitor | 可发现同一 Sandbox；经 CLI 查询有 35 类 `kata_*` metric families，包含 hypervisor 与 Guest CPU 等官方指标 |
| 删除 | 当前拓扑 Sandbox 消失、旧 VMM Host PID 退出、Monitor 不再列出该 Sandbox；runc 仍能 exec |
| Observer | 同 UID、零重启、eventsLost=0；末点 metrics collection errors=0，各 source lifetime refresh errors=0 |

Guest 标记阴性不单独作为“绝无事件”的普遍证明：本次有 runc 阳性对照、不同 Guest 内核、两个容器 CRI PID=同一 VMM 的佐证，且只对这个明确窗口/标记作结论。没有把指标返回的 Guest OS 聚合数据描述为本项目已实现 Guest 进程级探针。

VMM 与 shim 的实际 Host cgroup 不相同，路径也不应靠 Kubernetes cgroup 命名模板推算。保存了 `/proc` 得到的真实路径/inode。未检验所有 Pod/Host 限流、资源隔离或 CPU 口径的等价性；RuntimeClass 中的 overhead 是调度配置，不是实测恒定消耗。

删除期间上游日志有 `failed to cleanup container ... /run/vc/sbs/... no such file` warning，见 [日志](kata-20261027/success-journal.txt)，没有隐藏。第二次测试的当前拓扑清理已通过；最终第三次加强了 Host PID 退出及 Monitor 清理断言，两者也通过。它证明本次清理结果，不声称上游日志零 warning/所有异常路径均无残留。

## 留下什么、还没有做什么

测试恢复原 Agent DaemonSet spec；临时 namespace/Pod/锁由 harness 清理，原 Agent image 仍是 `:dev`。Kata 安装、RuntimeClass、回环 Monitor 与 tmpfs 服务按接入目标保留，使用新功能需部署本分支 Agent 并启用 monitor 参数。原 containerd 配置备份也保留。

最后实际复跑安装器的防覆盖路径，预期返回非零并明确拒绝已有 `/opt/kata`，不是第二次安装成功；[拒绝记录](kata-20261027/reinstall-refused.txt) 保留，前后 containerd 配置 SHA256 相同，自己创建的锁清理。最终检查原 Agent Ready/零重启、无测试 namespace/实验锁、无 Ready Kata Sandbox，Monitor 列表为空。受管服务 enabled/active；没有为了证明重启恢复而重启整台开发环境。

下一阶段 M8 应在这条身份链之上建立 **Sandbox 级 Host/VMM 视图**，区分 VMM 主线程、vCPU 与其他线程，再复用现有 eBPF CPU/runqlat 做实际 Host 调度测量；不要把共享 VM 回填成每个 Guest 容器各一份 CPU。Guest 进程探针及 Host/Guest 时间对齐属于后续里程碑，本次没有提前实现。
