# M10e：runc / Kata 配对运行时对照

日期：2026-11-13

环境：本地单节点 `kno-dev`（Minikube），未使用 `tdk`

原始数据：[m10e-runtime-20261113T083000Z](m10e-runtime-20261113T083000Z/)

## 结论

4 组 AB/BA 配对、共 8 个独立 Pod capture 均通过采集契约校验。Kata 相对 runc 的吞吐配对差值中位数为 `-5.10%`，探索性 bootstrap 区间为 `[-26.53%, +7.40%]`；区间跨过 0，当前数据不能支持“Kata 吞吐更低”这一方向性结论。

同一批 capture 中，Kata 的 operation P99 配对差值分别为 `+125.00%`、`+269.57%`、`+107.41%`、`+216.67%`，中位数 `+170.83%`，探索性 bootstrap 区间 `[+107.41%, +269.57%]`。这说明在本机、当前镜像与短时 SHA-256 + `sched_yield` 微基准下，4 对数据都观察到 Kata P99 较高；它不是其他内核、hypervisor、CPU 拓扑或真实业务的通用因果结论。

每个窗口都有少量超过 10 ms 直方图上界的 operation，比例为 `0.060%` 至 `0.125%`。所有窗口均低于 1% 的 P99 censor 门限，因此本次 P99 没有被标为截断；原始 overflow 计数仍保留在摘要中，没有通过重试隐藏。

## 方法与证据

- 奇数 pair 使用 `runc → Kata`，偶数 pair 使用 `Kata → runc`，降低固定顺序与宿主机漂移混淆；默认 4 对只作工程性短测，不承担统计外推。
- 两侧使用同一实际镜像 ID `sha256:b3abaa242582f1b7004815a3b24b559e0f65c11ce9aca602819ce46181522792`，容器均为 1 CPU request/limit、32 MiB request、128 MiB limit。Kata RuntimeClass 自身的 Pod overhead 不被伪装成相同资源。
- 每个 capture 创建新的 Pod UID，等待 Ready 后才从 Minikube node 经 Pod IP 发起同一控制请求；启动和 VM boot 不计入工作窗口。
- 原始 Pod、RuntimeClass、node、imageID 与 workload 参数由离线摘要器重新校验，不能只靠输出文件名认定 condition。
- runc capture 必须看到 Host container 且不能出现 Kata sandbox；Kata capture 必须看到 `guest-unavailable` container、sandbox 和正的 hypervisor PID。独立 Host 资源快照还按同一 Pod UID 校验 `runc-container` / `kata-sandbox` 归属。
- 每次 capture 后删除 Pod，并等到旧 Pod UID 与 sandbox 从 Agent 拓扑消失，避免后续窗口复用旧对象。
- Agent 在实验前后保持同一 Pod UID、同一 container ID、Ready、零重启；`eventsLost` 没有增加。临时 current-source Agent 使用后，原 DaemonSet pod spec 逐字节恢复。
- Host attribution 快照在 workload 之后单独采集，不把 Observer API map 扫描成本混入吞吐与延迟窗口。

工作负载方向从未作为脚本成功条件；只有身份、环境、采集完整性与数值自洽是门禁。完整的每对 throughput、P50/P95/P99、overflow、Pod UID 和归属证据见原始目录的 `summary.json` 与对应 capture 文件。

## 失败过程没有被隐藏

正式结果之前保留了 3 次失败和 1 次短 pilot，便于区分工具缺陷、部署版本与运行时边界：

1. [pilot 1](m10e-runtime-pilot-20261113/) 暴露了 runc topology 会省略空的 `sandboxes` 字段，而不一定返回 `[]`。采集逻辑改为同时接受 omitted/null empty collection；该次手工中止，退出码 130。
2. [pilot 2](m10e-runtime-pilot2-20261113/) 暴露了已安装的旧 Agent 不含 `/api/v1/host/resources`，不能验证本次新增的 Host attribution 契约。Make target 因而从当前源码构建临时 Agent，并在所有退出路径恢复原 spec；退出码 22。
3. [pilot 3](m10e-runtime-pilot3-20261113/) 暴露了 `kubectl port-forward` 对 Kata Pod 会连接 Host CNI namespace 的 localhost，而 benchmark server 位于 Guest。控制路径改为 Minikube node 直接访问 Pod IP，使 runc 与 Kata 使用同一可达路径；退出码 52。
4. [pilot 4](m10e-runtime-pilot4-20261113/) 用 2 对短窗口验证上述修正和清理/恢复路径后，才运行默认 4 对正式实验。

这些 pilot 不并入正式 effect 计算。正式目录的摘要只读取自身 8 个 capture，且脚本不会因为观察方向不合预期而重跑某个窗口。

## 边界与下一步

本次只回答“在一个可复现的本地节点上，Observer 能否用同一套身份与 Host 归属证据进行 runc/Kata 配对比较，以及这次短测观察到了什么”。它没有隔离所有 WSL2/Minikube 调度噪声，没有测 VM 启动成本、网络延迟或生产 SLO，也不能证明 Kata 固有开销。

若要把性能结论做得更强，应在受控 CPU 拓扑上增加 pair 数与窗口长度，记录宿主机背景负载，并把不同 Kata hypervisor/内核作为显式实验因子；在此之前，当前最诚实的表述是“吞吐方向不确定，当前 4 对内部 operation P99 均较高”。
