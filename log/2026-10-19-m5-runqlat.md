# M5 Run Queue Latency 实验记录

日期：2026-10-19
环境：WSL2 Ubuntu 24.04、Linux 6.6.114.1、Minikube 1.38.1、Kubernetes 1.35.1、containerd 2.2.1、cgroup v2

## 实验目标

- 验证 `sched_wakeup` / `sched_wakeup_new` 到 `sched_switch` 的 runnable 等待时间计算；
- 验证内核侧 log2 histogram 能区分 baseline 和 CPU contention；
- 使用独立的 cgroup v2 CPU pressure 信号验证趋势；
- 确认 exec、CPU hotspot、runqlat 三条链路可以连续运行。

## Workload

- baseline：1 个 worker，锁定到容器允许的第一个 CPU；
- contention：8 个 worker，全部锁定到与 baseline 相同的单个 CPU；
- 每个 worker 定期调用 `sched_yield`，确保产生可重复的 runnable 排队；
- runqlat 测量窗口：5 秒。

## 首轮结果

| 场景 | Count | Average | P50 | P95 | P99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| baseline | > 5 | - | - | 31 us | - |
| contention | 66,365 | 529.08 us | 1,023 us | 2,047 us | 2,047 us |

contention P95 约为 baseline 的 66 倍。调度事件只更新 BPF map，用户态仅在测量窗口开始和结束时读取累计快照。

第二轮结果：baseline P95 `31 us`，contention P95 `1,023 us`。同一轮 cgroup v2 `cpu.pressure` 的 `some total` 增量分别为 `89,510 us` 与 `5,940,045 us`，两种信号的变化方向一致。

Minikube 节点未安装 `perf`，因此选择 cgroup PSI 作为独立对照。

## 连续回归发现的问题

依次运行 lifecycle smoke、CPU hotspot smoke、runqlat smoke 时，runqlat 请求收到 EOF。Kubernetes 状态显示：

```text
Last State: Terminated
Reason: OOMKilled
Exit Code: 137
memory limit: 128 MiB
```

Agent 重启后、尚未运行 workload 时，CRI 统计已经达到：

```text
workingSetBytes: 121,016,320
usageBytes:      133,513,216
rssBytes:         77,623,296
```

根因是 LRU BPF map 按 `max_entries` 预分配，其内核内存计入创建 map 的 Agent cgroup。初始 runqlat 配置为 65,536 个 runnable timestamp、65,536 个 task identity、16,384 个 process stats 和 65,536 个 histogram bucket，在 128 MiB limit 下没有稳定余量。

## 修复

runqlat map 上限调整为：

| Map | 修复前 | 修复后 |
| --- | ---: | ---: |
| `runnable_since` | 65,536 | 16,384 |
| `task_identity` | 65,536 | 16,384 |
| `latency_stats` | 16,384 | 4,096 |
| `latency_histogram` | 65,536 | 16,384 |

该容量仍显著高于当前单节点 demo 的活跃任务数量。修复后的内存和连续回归结果记录在本文后续章节。

## 修复后验证

Agent 重新部署 5 秒后的 CRI 统计：

```text
workingSetBytes: 95,719,424
usageBytes:      95,719,424
rssBytes:        79,171,584
restartCount:             0
```

随后连续运行 lifecycle smoke、CPU hotspot smoke、runqlat smoke：

```text
lifecycle: workload exec event observed
CPU hotspot: 98.99%, ranked first
runqlat baseline P95: 31 us
runqlat contention P95: 2,047 us
cgroup CPU pressure baseline: 76,085 us
cgroup CPU pressure contention: 6,002,169 us
```

整套回归后 working set 为 `117,305,344` bytes，restart count 仍为 0。继续重复运行三轮完整 baseline/contention runqlat 实验后：

```text
restartCount: 0
memory:       118.1 MB
```

内存进入平台，没有随测量次数继续增长；三轮实验均通过 P95 差异和 PSI 趋势校验。

## 阶段 Review

- tracepoint 参数和 CO-RE 程序已在目标 WSL2/Minikube 内核实际加载；
- histogram bucket 并发初始化使用“插入 0 后原子加 1”，避免两个 CPU 首次命中同一 bucket 时丢计数；
- 用户态以 bucket delta 的总和作为事件数，避免 stats map 与 histogram map 非原子快照造成 percentile 分母不一致；
- API 串行执行按需 trace，防止多个大快照同时放大内存；
- workload 通过 OS thread affinity 把唯一变量限制为同核 worker 数量；
- 当前 P50/P95/P99 是 log2 bucket 上界，不是精确分位数；这是明确的精度/开销折中；
- 当前支持单节点短窗口诊断，map 容量和 Agent 开销将在 M6 基准完成后进入性能优化阶段。
