# M8：Kata Host/VMM 资源归属与 vCPU 调度实验

## 目标与交付

沿用 M7 的身份链，新增独立 `/api/v1/host/resources` 与 `kno top workloads`：Host runc container 与 Kata sandbox 同屏，但不混合记账域、不把共享 VM 的 CPU 重复归属给 Guest 容器。提供 VMM 线程 CPU/runqlat、vCPU 聚合等待、VMM RSS 和进程 IO 差值。没有新增 Guest Probe，也没有占用 Kata QMP 控制通道。

代码分为 namespace alias `3102681`、Host 视图/测试契约 `a1ddcf2`。最终测试镜像 `kubenode-observer/kno-agent:kata-vmm` 的 config ID 为 `sha256:00e5948a0e0af83ba6b13e1b6bb4a7e0cac9bf213d1659d12ae6e731ad72e516`；[构建输出](m8-20261103/final-build.txt)、[最终源码 HEAD](m8-final-20261103/m8-source-head.txt) 与 [源码 SHA256](m8-final-20261103/m8-source-sha256.txt)一并保留。构建发生在提交过程中，HEAD 元数据不用于替代内容指纹；本次测量的生产源码相同。

字段含义、来源、错误语义和复现入口见 [M8 指南](../docs/host-resources.md)及 [OpenAPI](../api/host-resources.openapi.yaml)。API 工程流程在这里落实为本地可 review 的契约、显式 null/partial 和结构化错误，以及保存真实响应后的离线 schema 校验；没有创建不必要的外部工作区或上传节点数据。

## 环境恢复与 PID namespace 陷阱

WSL2 Ubuntu / Linux `6.6.114.1-microsoft-standard-WSL2`，Minikube Docker-driver `kno-dev`、Kubernetes 1.35.1、containerd 2.2.1；节点 4 GiB / 12 CPU，Agent 默认 128 MiB / 200m 不变。Kata 4.3.1 Go runtime，包内 QEMU **11.0.1 kata-static**（[版本](m8-final-20261103/m8-qemu-version.txt)），Guest Linux 6.18.56。

开始时原节点容器退出（255）。启动同一个 `kno-dev` 容器、更新 kubeconfig 并启动节点 containerd/kubelet 后恢复 Ready；没有重建节点、拉取 Docker Hub 或调整 Windows/WSL 全局设置。M7 的节点私有 `/dev/shm` 1 GiB 与 Monitor 服务仍在。

节点是 Docker 容器，Node procfs PID 不等于 eBPF 全局 PID。因此不能直接拿 M7 的 VMM PID 去匹配 CPU/runqlat 的数值 key。本次在 CPU value 里增加 namespace PID/TGID，加载时指定 Agent 的 PID namespace；全局 key 和原 cgroup 记账保持不变。真实内核别名测试记录了 global PID `281262` → namespace PID `280188`（[完整 kernel test](m8-20261103/kernel.txt)）；早期独立测试也保留于 [namespace-kernel](m8-20261103/namespace-kernel.txt)。

线程有独立 starttime 与 cgroup；不假定 vCPU 和 QEMU 主线程在同一个 cgroup。验证稳定的 Node TID → 唯一全局 key 后才关联 runqlat。新线程、消失、重用、迁移、重命名、计数器重置/缺失以及扫描不完整，均不能被填成 0 或完整 VM CPU。CPU value 24→32 bytes，8192 项逻辑 value 增加 64 KiB；namespace helper 只在新明细 key 插入时调用。不据此承诺零额外开销。

## 尝试与失败保留

第一轮 [pilot](m8-pilot-20261103/exit.json) 退出 1，发生在 M8 测量前：Kata Pod、VMM 和拓扑正常，但官方 Monitor `/sandboxes` 暂时为空。节点重启后 Monitor 先于 `/run/vc/sbs` 建立 watcher，日志显示 60s 重试周期；原脚本立即 grep 的假设不成立。补成最多 90s 的就绪等待，没有改写 Monitor 数据或更换运行时。

独立的 [pilot2](m8-pilot2-20261103/exit.json) 通过，baseline/competition/recovery 的两窗 P95 算术均值分别 4095/32767/511 us。随后增加了“部分 vCPU 消失/改名或 procfs 线程扫描不完整时不能给出完整聚合”的回归测试并收紧实现，再构建最终镜像独立重跑。所有失败与成功目录均保留，未覆盖失败结果。

## 最终镜像的真实负载实验

[完整验收](m8-final-20261103/exit.json) 退出 0。复用 M7 独占锁/临时 namespace/恢复机制，只 pin 临时测试 VM 线程和临时竞争 Pod 到同一个允许 CPU，没有改全局 affinity/sysctl。

1. 双 Guest 容器共用一个 VM；API 只返回一条 `kata-sandbox`，同时有普通 `runc-container`。
2. QEMU 两个 `CPU N/KVM` 线程都通过 Node/global PID 和每线程 cgroup join 成功；分类来源明确为线程名启发式，不冒称 QMP 权威身份。
3. baseline 两窗；创建并 pin 四 worker Host 竞争 Pod；竞争两窗；删除竞争者；恢复两窗。每窗请求 5s，不同时跑 Go 编译或其他基准。

| 阶段/窗 | VMM CPU % | vCPU 等待数 | vCPU P95 us | 外部 schedstat CPU % |
| --- | ---: | ---: | ---: | ---: |
| baseline 1 | 52.73 | 2300 | 511 | 52.21 |
| baseline 2 | 56.10 | 2246 | 4095 | 54.85 |
| contention 1 | 12.30 | 1052 | 32767 | 12.23 |
| contention 2 | 12.35 | 1064 | 32767 | 12.24 |
| recovery 1 | 53.99 | 2318 | 1023 | 53.37 |
| recovery 2 | 53.20 | 2273 | 511 | 52.55 |

来源：[完整窗口汇总](m8-20261103/final-windows.json)、目录内 `m8-<phase>-<round>.json` 原始直方图和每窗 reference start/end。六窗均 `partial=false`、两个 vCPU，VMM RSS 269455360→269516800 bytes；runc memory 标记 `cgroup-memory.current`，VM 标记 `proc-status-rss`，没有将两者宣称为同一口径。Host IO 差值可返回有效 0，但不代表 Guest 没有 IO。

竞争时 VM runtime 份额下降、Host runnable 等待上升，移除竞争后反向恢复，支持“能识别 Host vCPU 调度竞争”的机制结论。不能据此比较 runc/Kata 性能优劣、隔离开销、统计显著性或跨环境绝对延迟。baseline 的 511→4095 us 波动本身也表明共享环境噪声，不能隐藏。

外部参照来自线程 `/proc/.../schedstat` runtime；窗口 5.49–5.91s 包住 HTTP，而 eBPF 实际窗口约 5.02–5.11s，因此只能做趋势对照，不能把两列差异当同窗精度误差。`sched_schedstats=0`，没有拿 waitNs 的零/历史量当延迟精度基准，也没有为了通过测试开启全局 sysctl。内核口径见 [procfs](https://www.kernel.org/doc/html/latest/filesystems/proc.html)和 [schedstats](https://www.kernel.org/doc/html/latest/scheduler/sched-stats.html)。

## 接口、边界与回归

真实 CLI 六窗成功；非法 duration 返回结构化 400，并发窗口返回结构化 429。保存的 9 个成功响应和 2 个错误响应通过 OpenAPI 3.1 / JSON Schema 2020-12 校验（[结果](m8-20261103/final-contract.json)）。未知/重复参数、405、503、取消、空筛选、线程/PID 代际、计数器回退、缺失不等于零等由 Go 测试覆盖。

[全套 Go test](m8-20261103/unit.txt)、[vet](m8-20261103/vet.txt)、[host/topology/probe/runqlat race](m8-20261103/race.txt)、[真实 BPF retention/batch/namespace/map-stats](m8-20261103/kernel.txt)与 shell 语法检查通过。retention 测试的低容量负面对照仍有明显丢失明细，不会被本次 alias 修改伪装为完整。

M7 的 Host exec 阳性 / Guest exec 阴性、不同内核、官方 metrics、删除后 topology/旧 VMM PID/Monitor 清理以及 runc 可用性均随最终验收通过。删除 VM 后新资源接口也不再返回旧 Sandbox。

最终镜像的 [runc 回归](m8-runc-20261103/exit.json)退出 0：[integration](m8-runc-20261103/integration.txt) 的 lifecycle、CPU hotspot（99.61%）、runqlat（baseline 31us / contention 2047us）均通过；[40000 子进程](m8-runc-20261103/stability.txt)后同 Agent UID、零重启、eventsLost=0，稳定性即时 RSS 54198272 bytes、Go heap 9456328 bytes。末点 [metrics](m8-runc-20261103/metrics-after.txt) 三 source ready、collection errors=0、各 lifetime refresh errors=0。原 DaemonSet spec 核对完全相同并恢复。CPU 明细容量仍为 8192，末点保留 7552 项不等于记录了 40000 个进程的无限历史。

最终镜像另跑原有 `--mode all`（[summary](experiments/m8-final-20261103/summary.json)，状态 complete）：4 组 AB/BA、每窗 10s，吞吐差异中位数 **−1.21%**、探索性 95% bootstrap **[−6.81%, +7.19%]**；P99 差异中位数 +5.88%、区间 [−5.88%, +18.75%]。区间跨零，样本少且运行在共享 WSL2，不声称性能改善、等价或零开销；这也是 Observer off/on 对照，不是旧版/新版 alias 成本的独立因果分解。

steady/churn × 250ms/1s/2s × 2 次，共 **12 个 CPU 精度窗口**：独立 cgroup 累计量对 `cpu.stat` 的最大名义绝对偏差 0.001363%，最大 reference bracket 0.002923%，resetKeys=0。这只是本机本负载有限窗口，不能推广为跨内核绝对精度。明细 `missingKeys` 各窗累计诊断计数为 0–19781（churn 后的 steady 也能淘汰历史项），不等于独立丢失进程数，更不是 ring buffer eventsLost；不能用准确的 cgroup 总量宣称有限进程表完整。若缺失命中 VMM 线程，M8 会返回不可用/partial；普通 runc 总量继续使用独立 cgroup 计数，不依赖明细列表求和。

最终 [环境与清理检查](m8-20261103/final-state-checks.txt)核对原 Agent spec、Ready/零重启、测试 namespace/Pod/锁均消失、Monitor 空、无 Ready Kata Sandbox；RuntimeClass、Kata 安装与回环 Monitor/tmpfs 服务按开发目标保留。`containerd config dump` 有已有 `untrusted_workload_runtime` 未知字段 warning，原样保留，没有据此修改运行时配置。首次故障的 Monitor journal 后补采自已有日志并标明 [late capture](m8-pilot-20261103/failure-monitor-late-capture.txt)，不是当时实时采样的冒充。

## 范围

本次仍限定单节点、单 VM QEMU/KVM 工程验证。procfs 和两组 BPF map 的快照不是跨源原子事务；LRU retention、尚未结算的运行片段、两个端点之间短暂变化均有边界。VMM RSS/IO 不等于 Guest 内存/块吞吐；vCPU 命名不是不可伪造身份。

M9 才进入 Guest Probe，M10 才做 Host/Guest 时间对齐与跨层分析；本次不提前混入两层进程指标。后续研究重点可以是区分“Host 抢不到 CPU”与“Guest 内部争用”，而不是继续堆普通节点字段。
